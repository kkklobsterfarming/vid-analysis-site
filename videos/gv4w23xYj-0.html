Actionable Insights

  • Start with one concrete failure and a small annotated dataset. Following the workshop’s 34:13 suggestion, collect about 20 traces as a learning exercise, not a statistically sufficient release test. In a proposed evals/trip-followup.md, define the task, evidence supplied to the judge, success, failure, and pass/fail examples. For a travel assistant, assess whether a follow-up answer uses the requested trip details rather than whether it is merely helpful. Include a generic answer that sounds fluent but ignores the request so the first experiment can reveal false passes.
  • Select the span that contains the evidence your criterion needs. At 25:31 to 26:03, DeLucia distinguishes root spans for input-versus-itinerary checks from tool spans for tool-output checks. In Arize, inspect the dataset preview before running a judge; use the demonstrated root-span condition parent ID equals null as a UI filtering concept, not a copied SDK expression. Confirm that each row contains the user request and the output being assessed. Missing context should produce an explicit insufficient-evidence outcome or manual review, not an invented judgment.
  • Instrument only what you need, then inspect one complete request. The workshop names OpenInference, whose repository identifies it as OpenTelemetry instrumentation for AI observability. Choose the integration for your framework, send a non-sensitive test request, and check parent-child relationships and input/output fields. Redact private content and secrets before exporting production traces. A visible trace tree is useful only if the fields needed for your rubric actually arrive.
  • Use code for exact constraints and a calibrated model judge for semantic ones. Check structured itinerary day counts, required keys, and numeric budget totals with deterministic tests when the data permits. Reserve the LLM judge for whether an answer addresses a follow-up in context. In the prompt playground, map dataset fields to the rubric’s variables, choose explicit labels, and inspect explanations for disagreements. This follows the workshop’s code-evaluation distinction at 6:07 and variable mapping at 29:09; it avoids paying a model to count a structured array.
  • Freeze a human-labeled holdout before iterating the judge prompt. Record rubric version, model version, dataset version, labels, and explanations. Compute false passes and false fails separately, then inspect every disagreement in the initial small set. The workshop introduces human alignment at 32:41 to 33:13; OpenAI’s evaluation guidance also recommends calibrating automated scores with human feedback. Do not repeatedly tune against the same holdout and still describe it as unseen evidence.
  • Attach a decision to the result before using it in CI. Write down which critical failures block a release, which uncertain cases require review, and how much change is acceptable on your task set. These are proposed workflow additions, not thresholds supplied by the speaker. Compare the candidate and baseline on the same cases and include judge cost and latency in the report. A 20-trace prototype is enough to uncover rubric mistakes, not to prove that rare production failures are controlled.

Core thesis

An eval is a structured test of a defined behavior. A trace records the instrumented steps of a request; an evaluator uses selected evidence to judge whether a criterion was met. DeLucia’s practical method is to inspect real examples, define one concrete quality, turn the criterion into a judge prompt, and compare the judge’s decisions with human annotations.

The workshop uses Arize’s travel-agent demo to make that process visible. Its strongest contribution is the path from a vague requirement to a reusable evaluator. Its weaker claims concern the boundary between ordinary tests and evals, and how much a trace or judge explanation can tell you about internal model reasoning.

Deep research and Verdict on the main claims

Specific, iterative evals are better than intuition alone

Verdict: agree, high confidence. OpenAI’s evaluation best practices recommends task-specific tests, representative datasets, continuous evaluation, and human calibration. This supports DeLucia’s method beyond her own product demonstration. It also warns against biased datasets and generic metrics, which limits what the workshop’s small demo set can establish.

The source is vendor guidance, not experimental proof that every implementation of this recipe improves an agent. A concrete rubric can still measure the wrong objective. The practical conclusion is to write the decision rule with the stakeholder who owns the failure, then collect examples that challenge it. Underemphasized in the talk is the need to distinguish an exploratory dataset from a release-quality holdout.

A model judge can supply useful quality labels

Verdict: agree with calibration, high confidence; disagree with treating its explanation as proof, high confidence. Zheng and colleagues, Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena, reports over 80% agreement between strong judges such as GPT-4 and human preferences in its studied settings. The same paper identifies position, verbosity, self-enhancement, and reasoning limitations.

That is supporting and contradicting evidence in the same source. Model judges can approximate human preferences, but their agreement is not universal and is not a demonstrated accuracy figure for this travel application. A plausible explanation helps a reviewer find mistakes; it does not establish that the label is correct. Hold out annotated cases, inspect false passes, and include adversarial examples that are fluent but fail the criterion.

One quality per evaluator is a sound starting rule

Verdict: agree as a design default, moderate confidence; mixed on its presentation as a general capability limit. At 19:55 the speaker invokes research for handling one criterion at a time, but the extraction does not identify a study establishing a universal rule. OpenAI’s guidance supports scoped tests and explicit criteria. The MT-Bench work supports useful model judging with limitations, not a blanket prohibition on multi-criterion prompts.

Separate evaluators make failures easier to interpret and can prevent a high style score from hiding a factual failure. They also add calls and cost. Combine criteria only after measuring whether the combined judge retains acceptable agreement for each criterion. The talk’s exceptions for decision models and agent judges are suggestions, not independently verified comparative results in this analysis.

Traces are necessary for evals, and evals differ categorically from tests

Verdict: mixed, high confidence. OpenInference supports the claim that AI applications can export instrumented telemetry through an OpenTelemetry-based ecosystem. In the workshop, traces help choose the right tool output or final answer for a dataset. They are particularly useful when diagnosing a multi-step failure.

However, OpenAI’s guide describes evaluation of single-turn model interactions as well as complex agents. Input-output pairs can support a black-box eval without a complete trace. Ordinary tests can check properties, schemas, and acceptable sets of outputs, not only one exact string. The talk itself recognizes code-based evaluation at 6:07. The useful distinction is the evidence and scoring method, not a categorical replacement of testing with a new term.

Decision judges and automatic improvement deserve experimentation

Verdict: uncertain, low confidence in comparative claims from this workshop. The transcript mentions recent decision-model products and Arize agents that can iterate prompts or investigate issues. The available evidence does not establish a general cost, latency, or reliability advantage over a calibrated LLM judge. Nor does automatic iteration prove that the resulting evaluator is better on unseen cases.

Treat this as an optional comparison: hold the labeled cases and criterion fixed, compare each judge’s false passes, false fails, latency, and cost, and review whether explanations are needed. The fetched OpenAI evaluation guide includes a notice that its Evals platform is read-only from October 31, 2026 and scheduled to shut down November 30, 2026. Its design guidance remains useful, but this analysis does not recommend starting a dependency on that retiring platform. It does not infer the status of the separate decision-model products from that notice.

Recommended workflow and why it matters

Define a failure, locate the evidence, label a few examples, and choose the least ambiguous scoring method. Use the judge prompt only for criteria that need semantic judgment. Iterate on a development set, then test on held-out annotations before attaching release consequences. After rollout, sample production disagreements and update the dataset without losing earlier regression cases.

The key result should be a decision someone can act on. A dashboard full of labels is not enough if nobody has specified which failures matter or checked whether the labels are trustworthy.
