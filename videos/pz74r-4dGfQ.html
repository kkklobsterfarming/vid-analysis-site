Core thesis

Agents can recover from bad instructions without reporting the wasted work. Holmes proposes evaluating completed traces and using repeated failures to improve skills. This is a workflow for maintaining agent configuration, not evidence that the model itself learns new weights.

Big ideas and timestamped moments

The port-search example at 8:28 is the strongest explanation of the problem. A task can finish correctly while spending extra time rediscovering environmental facts. Output-only evaluation misses that cost.

At 12:32, the explanation accompanying a grade becomes the input to a later improvement run. That makes the explanation consequential: a mistaken diagnosis can produce a bad skill edit. Verdict

Agree, high confidence, that full traces reveal avoidable work hidden by successful outcomes. The tool-call example gives a concrete diagnostic target and the evaluation guide supports checking both process and outcome. Use failed-call counts and elapsed time alongside qualitative scores.

Mixed, moderate confidence, on automatic skill improvement. The mechanism is credible and publicly documented, but changes still need regression testing and human review. The underdeveloped part of the talk is measuring false-positive diagnoses, review burden, and evaluation cost. A score increase after an edit is an association, not a controlled causal estimate.

Disagree, high confidence, with reading the title as proof of deliberate concealment. The evidence describes unreported recovery behavior. It does not establish an agent’s motive.

Practical takeaways / recommended workflow

Assistant proposal: sample a small set of completed sessions, remove secrets, and have a person classify intentional interruptions before using the traces for automated scoring. Compare one proposed skill edit against an unchanged version on held-out tasks. Track task success, total cost, and time, including the scorer’s cost. Keep the previous skill version available for rollback. This evaluation design is an addition to the talk, not a demonstrated command sequence.

My read / why it matters

The practical contribution is diagnosing configuration debt from actual tool use. The case for collecting richer evidence is stronger than the case for letting a score-driven process rewrite instructions without oversight.
